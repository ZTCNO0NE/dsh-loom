# Agent 从上下文到自进化：关系图系列

## 总原则

这一组图不把 `context`、`memory`、`input body`、`skill`、`tool`、`MCP` 当同义词。每张图统一回答四个问题：

1. 它从哪里来？
2. 它在哪一轮进入模型或执行器？
3. 它能影响什么？
4. 它不能替代什么？

图中的 Codex/adapter 链路仅指本文核查过的**本机示例部署**。概念图会把“通用 Agent 模式”和“该部署的具体实现”分开标注，避免把一个实现细节讲成行业事实。

## 图谱与阅读顺序

| 顺序 | 单图问题 | 读者带走的关系 | 关键反误解 |
|---|---|---|---|
| 01 | 一次请求到底由什么组成？ | 用户话语、稳定指令、状态、能力目录与工具结果共同构成本轮工作包 | 用户消息不等于全部上下文 |
| 02 | context 和 memory 是什么关系？ | context 是本轮可见工作区；memory 是可被选择、压缩、检索并重新注入的状态来源 | 有历史不等于模型已理解或已学习 |
| 03 | input body 怎样被构造？ | `input`、`instructions`、`tools`、推理/并行等设置在请求体中分别存在 | 一段 prompt 不能代表整个请求体 |
| 04 | skill、tool、MCP 分别站在哪？ | skill 提供做事方法；tool 提供受限动作；MCP 是可提供 tools/resources 的协议连接层 | skill 不是执行器；MCP 不是某一个工具 |
| 05 | 工具调用如何回到下一轮？ | 模型提出调用，执行边界运行，结构化结果回灌 context/state | 模型发出调用不代表事情已经发生 |
| 06 | 服务侧做了什么？ | 状态展开、协议转换、工具兼容与守门让客户端请求能与上游模型协作 | 状态展开不等于长期记忆治理 |
| 07 | 什么东西应该被长期保存？ | 事实、证据、候选、验收与回滚记录应可追溯；临时推理不应直接升格为事实 | 一次反思不等于可复用经验 |
| 08 | 核心架构图：所有对象怎样组织？ | 上述对象在“意图→工作包→执行→状态→改进控制面”的全局结构中各司其职 | Agent runtime 与自进化控制面不是一层 |

建议发布顺序：先发图 01 + 图 08，让读者有地图；随后每次文章或视频只展开 1–2 张局部图。图 07–08 在 Loom 专项篇中再进入真实验证、Gate 与 rollback。

## 图 01：本轮工作包（上下文的组成）

**关系主句：**本轮 context 是被组装出来的工作包，不是聊天框里最后一句话。

阅读顺序：用户意图（本轮变化）→ 稳定指令/项目规则（长期约束）→ 历史与已知状态（可恢复事实）→ skills/tools/MCP 暴露的能力目录（能做什么）→ 工具结果（刚发生的事实）→ 本轮工作包。

必须画出两个边界：

- 输入来源在进入工作包前彼此分开，避免误解为“全都是 prompt”；
- 工具结果在下一轮才成为可见信息，避免误解为模型能直接接触外部世界。

不能画：模型大脑、记忆库等于 context、用户消息直接到模型的单线。

## 图 02：context 与 memory

**关系主句：**context 是本轮工作台；memory 是候选材料库；二者之间存在选择、压缩和注入，而不是自动全量复制。

画面采用“工作台—档案库—检索闸门”剖面：

- 上层透明工作台：本轮任务、指令、最近工具结果，亮度最高，回合结束可消失；
- 下层档案层：会话历史、持久文件、项目约定、用户偏好、实验记录，以不同介质分层存放；
- 中间检索闸门：只能将与任务相关、预算允许、来源可辨的片段送回工作台；
- 右侧压缩器：长历史可以转为摘要，但摘要旁必须保留“可回源”细线；
- 红色虚线：未经验证的模型猜测不能直接沉入档案层。

必须给出三种状态标记：`本轮可见`、`可检索`、`已验证事实`。这是整套系列的认知骨架。

## 图 03：input body

**关系主句：**请求体是字段分工，不是一段长 prompt。

画面是“一只展开的信封/请求容器”的剖面，而非 API 文档截图：

- 容器内五个并列隔舱：`input`（当轮消息与结果）、`instructions`（稳定行为约束）、`tools`（名称/参数 schema）、`reasoning`（推理设置）、`execution settings`（如并行工具等运行参数）。
- 侧边画一条来自 `previous_response_id` / conversation 状态的历史展开支路，落入 input 隔舱；说明它接续会话，但并不自动提炼事实。
- 容器离开客户端后进入 adapter 的翻译门；此图只画到翻译门，不画上游 chat body，下一图专讲。

事实边界：字段名/存在形式只能表述为“本文核查的本机 Codex + adapter 示例”；图注必须保留这一限定。

## 图 04：skill、tool、MCP

**关系主句：**skill 说明“怎样做”，tool 提供“能做什么动作”，MCP 是把外部能力接入目录的协议层。

采用三层舞台而不是三栏对比：

- 顶层 skill 是一本带流程页签的操作手册；它影响模型的决策和步骤，但不能直接执行。
- 中层 tool 是带参数孔位的受限机械接口；模型只能按 schema 提出调用。
- 底层 MCP 是远端能力的接驳总线，可提供 tools/resources/prompts；它不是执行结果，也不等于单一 tool。
- 从 skill 到 tool 只画“建议如何调用”的虚线；从 MCP 到 tool/resource 画“注册/暴露”的实线；tool 到执行器画“实际调用”的实线。

反例注脚：把一段 skill 文本写得很好，不能绕过工具权限；接上 MCP，也不能自动得到可靠的任务规划。

## 图 05：一次工具调用的闭环

**关系主句：**模型只提出调用；执行器才让动作发生；结果必须结构化回灌，下一轮才能据此调整。

阅读顺序严格为：模型动作提议 → schema/权限预检 → 外部执行器 → 原始结果 → 结构化 tool output → context/state 更新 → 下一轮模型。

画出两条不同的失败路：

- 预检失败：动作没有执行，错误直接回到模型；
- 执行失败：执行器返回事实结果，不能被模型悄悄抹掉。

不要把“工具调用”画成模型伸手触摸文件系统；中间必须有执行边界。

## 图 06：客户端与服务侧的协议适配

**关系主句：**客户端负责组装请求；adapter 负责把状态和能力转成上游可理解的协议；两者共同组成一次可运行的调用链。

画面用“两个透明舱之间的翻译桥”：

- 左舱是 Codex client：input、instructions、tools、response chain；
- 桥中央是 adapter：展开 `previous_response_id` / conversation state，过滤或映射兼容工具，把 Responses 结构转换成上游 chat body；
- 右舱是 upstream model/provider：接收翻译后的 body，返回文本或 tool call；
- 底部回程：tool output 回到 Responses-style item，重新成为下一轮输入。

此图不放性能或“全平台”结论；只在桥旁标注“本机示例实现”。

## 图 07：从运行轨迹到可复用证据

**关系主句：**轨迹可以保存发生过什么；只有经过来源、验证和回滚约束的记录，才适合作为长期改进依据。

画面是一条由浅到深的证据阶梯：

`原始事件` → `可引用事实` → `可证伪假设` → `受限候选` → `独立验证记录` → `安装/回滚 receipt`。

每上升一级必须显示新增条件；失败记录留在链中，不被删除。最后一格才允许向 Loom 控制面交付“可评估的候选”。

## 图 08：核心架构图

**关系主句：**完整系统由四个大层组成：意图与约束、工作包与能力、执行与状态、改进控制面；每层的职责和可修改范围不同。

### 第一层：意图与约束

用户目标、稳定 instructions、项目文件/规则、权限策略。它们定义本轮任务与不变量。

### 第二层：工作包与能力

context assembler 从输入、检索到的 memory、skills、tools/MCP catalog、工具结果构造本轮工作包。此层决定模型“看见什么、可以提出什么调用”。

### 第三层：执行与状态

模型提出行动；tool runtime/preflight/MCP server/外部环境执行；结果返回 response state、会话历史与事实记录。此层决定动作是否真实发生。

### 第四层：改进控制面（Loom）

observe → hypothesis → candidate → independent verifier → gate → cold install / rollback。它只从经过证据化的状态读取，不能绕过第三层直接修改运行中的 runtime。

### 跨层规则（必须在总图中可见）

- 上游信息流：意图与约束向下进入工作包；执行结果向上回灌状态。
- 能力流：skill 指导调用；tool/MCP 暴露可调用边界；执行器拥有实际副作用。
- 进化流：事实记录进入控制面；只有 Gate 批准的冷替换在回合边界影响能力层。
- 信任边界：Verifier、Gate、回归集、权限策略构成 TCB，候选不能写入。

总图的画法使用“纵向四层 + 横向三条流”的剖面，不使用单纯盒子箭头：信息流画为蓝色纤维，能力流画为青色接口总线，进化流画为琥珀到绿色的独立环；TCB 是贯穿第三、四层之间的深色连续膜。

## 制作门禁

每一张图都必须有：

1. 一句关系主句；
2. 固定阅读顺序；
3. 明确“不代表什么”的反误解；
4. 确定性文字层和坐标/避让规则；
5. 图注中的事实范围与证据链接。

没有这五项，不进入生图队列。
