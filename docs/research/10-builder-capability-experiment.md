# Builder 能力实验：策略重写型行为模式（设计）

更新：2026-08-16。目的：设计一个**充分体现 builder 能力**的实验——actor 单独无法解决，必须由 builder 对 actor 做"方向级重写"（结构性、多行协调的更改），并且 naive 修复必须被淘汰。

## 1. 判定标准：什么才算"builder 不可替代"

实验要同时满足四条，缺一条都只能证明"actor 够强"或"修个小参数"：

1. **actor 单独失败（off 基线）**：当前配置下任务族持续低完成率，且 actor 没有自改能力（或自改被禁），改善只能来自 builder+gate；
2. **修复是结构性的**：不是改一个参数，而是**多行协调的策略包**（如：加技能 + 调工具链 + 加系统提示约束）；
3. **naive 修复无效**：只调单点参数能过隔离验证，但外环指标不改善 → 被回滚/继续迭代；只有策略包让指标真实变好；
4. **泛化**：换一组相似任务，同一策略包仍然有效（证明 builder 学到的是"方向"，不是过拟合单任务）。

## 2. 实验场景：从"通用文本编辑"到"验证纪律驱动"

任务族（10 个任务，外部断言判定）：

- 5 个"陷阱任务"：表面是简单文本替换，实际需要修改后**运行相关测试/校验**才能算完成；不做验证的 naive 修改会隐性破坏。
- 3 个"控制任务"：与陷阱无关的普通任务，用来检测回归。
- 2 个"泛化任务"：另一批同类陷阱（不同仓库/语言），验证策略包可迁移。

预期 off 行为（actor 单独）：陷阱任务完成率低（约 0-2/5），且重复犯同一类错误——"改了不验证"。

## 3. builder 必须产出的"方向重写"（策略包）

一个候选策略包至少包含多行协调变更：

| 变更 | 层 | 作用 |
|---|---|---|
| 新增技能："编辑后必须运行相关测试/校验" | skill（M4） | 改变做事流程 |
| 调整工具链：测试/编译工具的路径、超时、工作目录 | config/tool（M4） | 让验证可执行 |
| 系统提示增加验证纪律约束 | skill/prompt | 行为方向约束 |

单点 naive 修复（例如只加大超时）必须**通过隔离验证但外环不改善**——这是实验关卡 1 的淘汰条件。

## 4. 四关卡验收

| 关卡 | 内容 | 通过条件 |
|---|---|---|
| 1 naive 淘汰 | 让 builder 先出单点修复 | 外环指标不改善 → 回滚/继续迭代（不得上线停留） |
| 2 策略包通过 | builder 出多行协调变更 | 隔离验证（组合树/技能加载/回归/不变性）+ 外环 Δsuccess > 0 |
| 3 无回归 | 控制任务集 | 完成率不降、快照仍绿 |
| 4 泛化 | 换 2 个同类任务 | 复用策略包仍有效（或只需小修） |

## 5. 指标与对照

| 指标 | 定义 | 对照 |
|---|---|---|
| 完成率 | 陷阱任务外部断言通过占比 | off 基线 vs 插件开 |
| 效率 | 每任务动作数/耗时 | off vs on |
| 重复错误率 | 同类错误在 epoch 内重现次数 | 收敛性 |
| 回归 | 控制任务完成率 | 不降 |
| 泛化 | 泛化任务完成率 | >0 且可复用 |
| 收敛 | 连续 2 epoch 无同类补丁 | 插件行为 |

off 基线锚点已有：自建冒烟 5/5（27b 与 V4 Flash 各一条）、TB 切片 1/2。本实验新增"陷阱任务族" off 基线。

## 6. 为什么这能证明 builder（而不是 actor 自愈）

- actor 没有自改工具，且"换整套行为策略"不在它的行为空间内——它只会继续用当前策略尝试；
- 策略包是多行协调变更，builder 的独立世界模型（world-model.json）需要记录"哪些行为面要一起改、预期事件模式是什么"；
- verifier 的 first_divergence 会逐条暴露"改了技能但没配工具"这类半吊子方案，回炉逼 builder 补全——这正是深度调整的核心循环。

## 7. 对 M4 的硬需求（由实验反推）

1. `targetKind: 'skill'`：技能 patch 的内容/引用/参数校验（prime-agent validateEdit 风格的白名单）；
2. `targetKind: 'tool'`：工具模块的**隔离加载即校验**（fresh process import，语法/依赖/初始化错误直接 rejected）；
3. 回归集要覆盖"改技能/工具后，原行为不回归"（配置不变性扩展为行为面不变性）；
4. 系统提示技能行（prompt 类）的 patch 支持与内容校验。

## 8. 实施顺序

1. 先造陷阱任务族 + off 基线（actor 单独跑，记录完成率/错误模式）；
2. 按关卡 1-4 设计合成验证（A3/A4 扩展：策略包合法、技能加载、多行变更的预期轨迹）；
3. M4 实现 skill/tool patch 与隔离加载校验；
4. 端到端跑四关卡，记录 run-log。

## 9. 从零成长实验（2026-08-16 用户提议，作为主实验）

比"修行为模式"更直观、更有说服力的版本：**actor 从一个几乎空白的 loop 开始，由 builder 按用户意图逐步补齐能力，直到能完成任务；然后新任务超出它时，再触发 builder 继续完善**。观众看到的是"agent 被另一个 agent 从零养大"的完整轨迹。

### 9.1 起点：bare loop

- actor = 最简 profile：agent loop + 无工具/无技能（或仅 1 个基础工具），固定最小提示词；
- off 对照：bare actor 单独跑任务阶梯，第一步就失败，且永远停在原样（无自改能力）。

### 9.2 任务阶梯（逐步升级，外部断言判定）

| 级 | 任务类型 | 需要的补齐 |
|---|---|---|
| L1 | 创建/写文件 | 新增 fs 工具行 |
| L2 | 跑命令并汇报 | 新增 bash 工具行 |
| L3 | 编辑文件后验证 | fs + bash + "编辑后验证"技能 |
| L4 | 跨文件小重构 + 测试 | 多工具 + 验证纪律提示词 |
| L5（泛化） | 新领域任务 | 新技能/工具组合 |

每一级先由 actor 失败（off 或当前配置失败）→ 触发 builder → builder 产出**新增行/技能/prompt** → verifier 隔离校验 → 应用 → actor 重试 → 成功才进下一级。

### 9.3 说服力来源

1. **可见成长轨迹**：每级"失败 → builder 出手 → 验证 → 能力 +1"，全程留痕（signals/triggers/patches/history/run-log）；
2. **无混淆变量**：不是"修好一个已配置的 agent"，而是从零证明 builder 的设计能力；
3. **回归内建**：加 L2 时 L1 必须仍绿（新增行不能破坏旧能力）；
4. **泛化收尾**：L5 新领域任务证明学到的是"完善方法论"，不是背题。

### 9.4 指标

| 指标 | 定义 |
|---|---|
| 成长步数 | 从 bare loop 到全任务通过所需的 builder 迭代次数 |
| 每步 Δ | 该级任务 before/after 完成率 |
| 回归率 | 新增能力后旧级任务失败占比（必须 0） |
| 验证成本 | 每步 verifier/builder 的 token 与轮次 |
| 收敛 | 同级连续 2 epoch 无重复补丁 |

### 9.5 对 M4 的硬需求（从零实验直接逼出）

1. **builder 必须能"新增行"**：不只是覆盖现有 config，而是 `- insert` 新的工具/技能/提示词行——gate 的 patch 语义要从"整行覆盖"扩展为"插入新行 + 引用 builder 写的模块文件"；
2. **builder 要能写模块文件**（工具代码/技能定义/提示词文本），verifier 做隔离加载即校验（M4 规则落地）；
3. **回归集随成长增长**：每级完成后把该级任务固化进回归集，下一级验证必须全绿；
4. **profile 可重载**：新增行应用后 actor 以新配置重跑（HMR/loader update 或新进程）。

### 9.6 信任边界不改变（防"builder 直接改 actor"）

从零实验里 builder 确实要**写文件**（工具代码/技能定义/提示词），但这不等于"直接改 actor"。机制上必须钉死：

1. **builder 只写 staging 草稿**：builder 的输出一律落在 `meta-validate/workspace/<session>/builder/staging/`（候选文件），**绝不写 actor 的 live profile/运行时树**；
2. **verifier 只验草稿**：隔离加载即校验的对象是 staging 文件 + 候选组合树（`--dump-config` 含候选 overlay），验的是"这些草稿装上后能不能跑"；
3. **安装/覆盖只归 gate**：verifier 通过后，由 gate 把 staging 文件复制/链接进 profile 并插入行——这一步才叫"覆盖"；builder 不拥有写 live 树的权限；
4. **覆盖安全网不变**：应用前快照 before → 冲突检测（plan→apply 期间 profile 被改即拒）→ 安装 → 冒烟 → 失败回滚；**新增文件不得覆盖已存在的文件**（冲突即拒，用新文件名或失败），行插入优先 additive（insert），覆盖现有行仍需整行重述全部键；
5. **loop 层仍锁死**：builder 的 targetKind 白名单仍是 config/tool/skill，不能改 agent loop；
6. **TCB 路径只读**：regressions/ 与 verifier 代码对 builder 只读，builder 写的 staging 草稿也进不了 TCB 目录。

一句话：**builder 负责"起草"，verifier 负责"审稿"，gate 负责"出版"**——actor 的 live 树只有 gate 能碰，且必须在 verifier 通过之后。

### 9.7 实施顺序（更新）

1. 搭 bare-loop profile + 任务阶梯 + off 基线（actor 单独卡在 L1）；
2. **M4 最小集**：insert 新行语义 + skill/tool patch 类型 + 模块写入 + 隔离加载校验；
3. 从零端到端跑 L1-L5，全程 run-log；
4. 用 §1-§7 的"行为模式/泛化"实验作为 M4 后的进阶验证。
