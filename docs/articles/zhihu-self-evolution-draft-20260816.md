# Agent 不能自己进化自己，除非有人站在它外面

> dsh-loom（织机）工程笔记：一个"第二验证器"插件的设计为什么长这样

把一台本地 27B 接进 DeepSeek Harness 的第一天，我让它写一个文件。它回复我：我没有写文件的工具。这不是模型笨，是它根本没有那个能力，而且它不知道自己缺。

给它配一个"外部教练团队"之后，同样这个 agent，三天后：工具自己长出来了，行为习惯自己长出来了，连"模型太慢该换掉"都是它自己想出来的。整个过程中，我没有改过一行它的配置。

这篇文章不讲概念，讲翻车。我把这个系统设计过程中踩过的每一个坑，对应到一句设计结论上。你看完会明白：为什么自进化必须硬约束、为什么角色必须完全独立、为什么职责必须分离——不是因为洁癖，是因为每一步都付过真实代价。

## 一、先看三个真实痛点：谁做自进化，谁踩过

### 1. 它看不见自己缺什么

#### ① 例子：裸 agent 跑三个任务，0/3

我们把所有工具禁掉，只留一个 agent loop，让它做三件事：写文件、列目录、编辑文件后验证。结果全失败。单独看每一个失败都"合理"：没有 fs 工具，当然写不了文件。

但关键不是失败，是它失败之后的反应：它只会道歉、换一种说法重试、或者干脆放弃。它不会说"我缺一个写文件的工具，请给我装上"。因为它看不见自己的工具清单，看不见自己的配置，看不见自己为什么失败。

#### ② 为什么"多给点上下文"救不了

有人说：把工具清单塞进 system prompt 不就行了。问题是：塞进去它就知道"缺"吗？知道缺，它就能"造"吗？造出来，它敢保证"能用"吗？

这三件事，一件比一件难，而且全都发生在它自己的视角之内。一个人不能通过照镜子发现自己后脑勺缺了一块头发——除非有人站在他身后。

### 2. 它给自己当裁判

#### ① 例子：模型"觉得"改对了

让模型自己判断自己的修改对不对，最经典的翻车是：它把 JSON 改成了合法 JSON，然后说"改好了"。它没有跑校验，但它"觉得"没问题。任务要求是"必须输出 valid 证据"，它输出了一段自我感觉。

这不是态度问题，是结构问题：它既是选手，又是裁判。裁判和选手是同一个大脑，任何不利证据都会被"合理化"掉。Gödel 第二不完备定理说的是数学，落到工程上就是一句话：一个系统不能成为自身延续的最终权威。

#### ② 为什么"让另一个模型打分"也救不了

有人会说：那让 GPT-5 当裁判？问题变成：裁判和选手共享多少上下文？如果裁判看到的是选手自己整理的"我改得很好"的摘要，它等于在帮选手圆谎。如果裁判只看真实帧，那它和选手之间必须有一条信息隔离的边界——这就是后面要讲的"完全独立"。

### 3. 它替换不了运行中的自己

#### ① 例子：改配置改崩了整个会话

最疼的一个坑：我们最初让 builder 直接改运行中的 loader 配置，第一次生效了，第二次同一个会话里再改，loader 的条目树从 78 条塌缩成 2 条——进程直接崩掉，用户当前会话陪葬。

正在运行的 loop 不能原子地替换自己。任何热修改都可能在状态中间被打断，改错了还没有外部兜底。

#### ② 为什么必须冷替换

冷替换的意思是：修改不落在运行中的对象上，而是落在"下一次启动会读的文件"上，在回合边界停掉旧状态、加载新配置、失败了回滚到旧快照。用户听到的提示是"reload 后生效"。丑，但是稳。

## 二、痛点的根源：自指困境

这三个痛点不是三个独立 bug，是一个根源的三个面：**被修改者不能同时是观察者、设计者、裁判、执行者。**

### 1. 三个角色为什么必须分开

#### ① 观察者与被观察者不能是同一个

agent 的轨迹全部由它自己产生。它不知道哪些失败是环境问题、哪些是能力缺口、哪些是它反复绕圈。观察者必须站在 loop 外面，拿到的信息不能经过被观察者的"筛选"。

#### ② 设计者与裁判不能是同一个

设计者（我们叫 builder）负责"想改什么、怎么改"，裁判（verifier）负责"改了之后真的对吗"。两者一旦共享，就回到自己给自己打分。

#### ③ 执行者与被修改者不能是同一个

执行者（gate）负责安装和回滚，被修改者（actor）是运行中的 agent。执行者如果住在被修改者的肚子里，那被修改者就永远够得着验证链路——自进化退化成自我欺骗。

### 2. 硬约束不是保守，是对着痛点长的

#### ① verifier 不进 LLM 判定

verifier 的裁决只来自三样东西：候选的预期轨迹、隔离环境里真实跑出来的帧、回归集。逐字段/哈希对齐，第一次分歧就拒。LLM 在这个环节没有任何发言权。因为"让模型判断"就是前面那个翻车的裁判。

#### ② builder 输出默认不可信

builder 写出来的模块、schema、技能，默认按"有毒"处理：语法要过 `node --check`，模块要在隔离环境真实加载，参数 schema 要过 dsh 的校验。我们抓过 builder 生成的工具缺 `inject` 声明、schema 非法——模型写代码会错，这不是 bug，这是常态。

#### ③ loop 层第一版锁死

第一版只允许改 config、tool、skill。改 agent 自己的 loop？锁死。不是不想，是验证链路的成熟度还没到。先证明"加个工具不会把系统弄坏"，再谈"换个循环"。

## 三、我们的做法：外部教练团队

### 1. 五步回路

#### ① observe → judge → design → verify → install

- **观察**：收集失败信号、完整轨迹帧、回合时延、错误率；
- **判断**：一个只读关键摘要的"监督员"决定值不值得动手（有确定性证据时强制动手）；
- **设计**：builder 拿全量信息设计候选 patch，并声明预期轨迹和沉淀的偏好；
- **核验**：隔离环境真实执行，预期轨迹 vs 真实帧逐字段对齐，回归全绿才算过；
- **安装**：gate 写持久化 overlay，标记 reload 生效，失败回滚。

每装完一次，监督员会再看一次，直到没有值得改的证据。

### 2. 用真实案例证明

#### ① 案例：从零养大

裸 agent 三个任务 0/3。改进模型逐级生成并安装：四个工具（写文件、列目录、执行命令、读文件），两个行为技能（编辑后必须验证、JSON 结构校验）。最后同一批任务 5/5，严格对照 Δsuccess +3，旧能力回归不降。

#### ② 案例：它自己决定换模型

agent 被配成了 `qwen/qwen3.6-27b`，但路由到了根本不提供这个模型的官方 API，连"回复一句话"都失败。没有任何人提示它换模型。监督员唤醒改进模型后，它自己把默认模型改成 `deepseek-v4-flash`，安装后监督员再次被唤醒，它又迭代成 `deepseek-chat`。两次修改的 before/after 都留档。

#### ③ 案例：用户一句话，不需要 agent 自觉

用户直接说："sleep 1 总是 500ms 被杀掉，把超时调大。"没有让 agent 调用任何特殊指令。插件自动消化这条消息，监督员唤醒改进模型，超时从 500ms 调到 10000ms，核验通过、安装生效。用户想知道进度，直接问 agent："优化进度怎么样？"——agent 会查工具，如实回答。

## 四、为每个设计决策找一次真实翻车

### 1. 为什么"硬约束"：因为模型会绕过

#### ① 例子：builder 产物里的非法 schema

builder 生成的工具模块，第一次隔离加载就报错：参数 schema 里写了 `required: false`，dsh 不接受；另一个模块忘了 `inject: ['tools']`，工具根本注册不上。如果"模型写出来的就信"，这些错误会直接进生产。硬约束不是不相信模型，是模型本来就会错。

### 2. 为什么"完全独立"：因为共享上下文会污染

#### ① 例子：让同一个上下文既当选手又当裁判

最早我们试过让 actor 自己"感觉哪里不对再自改"，结果它把所有失败都归因于"环境"，把改动越做越小，最后什么都不改。把裁判和选手塞进同一个上下文，裁判会被选手的叙事带偏。后来 verifier 只读真实帧，不看任何一方的"总结"，翻车率立刻不一样。

### 3. 为什么"职责分离"：因为一个角色干多件事必有一件干不好

#### ① 例子：执行器不能同时是验证器

安装和验证是两种气质相反的工作：验证要慢、要全、要怀疑；安装要快、要原子、要能回滚。让同一个角色既判案又行刑，它会在"我装的应该没问题"的心理下跳过验证。我们现在让 gate 只负责写文件和回滚，它连"这个 patch 对不对"都不用知道。

## 五、它现在能做到哪一步（诚实清单）

### 1. 已验证

- 从零成长：0/3 → 5/5，Δsuccess +3；
- 自主换模型：qwen3.6-27b → v4-flash → deepseek-chat；
- 用户一句话改运行时，不需要 agent 自觉；
- 后台预约式优化：不卡对话，完成通知"reload 后生效"；
- 偏好沉淀：builder 声明偏好 → preferences.json，跨会话可见；
- 99/99 单元测试；Terminal-Bench 2.1 官方切片 fix-git PASS；
- npm（dsh-loom@1.0.2）与 GitHub 源两条安装路径均已实测。

### 2. 边界

- 第一版只改 config / tool / skill，loop 层锁死；
- 行为类技能是"显著提高概率"而不是确定性保证；
- 验证成本 = 一轮完整任务 token，用最小回归集控制；
- dsh 还是 developer preview，接口会变，注入点收敛在一个文件里。

## 写在最后

这套系统能跑，不是因为模型变聪明了，而是因为**没有人让模型对自己负责**。改进模型负责想，核验器负责怀疑，执行器负责动手，agent 负责干活。每一个角色都被硬约束按在自己的位置上，谁也别想越权。

你的 agent 不需要学会"自我进化"这件事。它只需要知道：遇到搞不定的事，有人站在它外面。
