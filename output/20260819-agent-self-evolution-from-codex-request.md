# Agent 为什么会反思，却很难真正进化？从一次 Codex 请求说起

我最近反复遇到一种错觉：Agent 读了报错，写了一段复盘，又重新调用工具，看起来已经在“自我进化”。任务拉长后，它仍可能重复读文件、反复试同一条命令，或把一次偶然成功当成通用经验。**会反思**离可靠地变强，还隔着一整套运行时。

为了把这件事讲清楚，我没有先从大词开始。我先看了一次自己本机的 Codex 客户端和 adapter 服务端，到底往模型那里送了什么。不同客户端和部署细节当然不同。这条链路足够把 Agent 去神话：模型读取的是一份被不断拼装、更新和裁剪的工作包。

## 一、先别谈自进化，看看一次 Agent 请求里装了什么

### 1. 用户说的一句话，只是工作包的一小块

#### ① 任务、规则、工具和历史是分开的

在我本机的 Codex 链路里，客户端会把当前任务组织为结构化 `input`，再单独放入稳定的 `instructions`、工具声明、推理配置和并行工具设置。**用户消息**只是其中一项，不是模型看到的全部。

把它翻成人话，这像把一个新同事交给项目组：你不仅告诉他“修这个 bug”，还要给他团队规范、他能用的工具、上次做到哪里、刚刚运行命令的结果。少了任何一项，他都可能从错误的地方开始。

```text
当前任务
  + 稳定规则与技能说明
  + 历史消息与当前状态
  + 工具目录与参数约束
  + 工具执行结果
  + 环境/工作区的已知信息
  = 本轮交给模型的工作包
```

#### ② 工具是一张受限的接口卡

模型不会凭空拥有读文件、改代码或运行命令的能力。它拿到的是一份**工具目录**：工具叫什么、参数长什么样、输出会回到哪里。模型先提出调用，外部执行器再真正做事。结果会以 `function_call_output` 或 `custom_tool_call_output` 一类的结构化项目回到下一轮上下文。

这也是为什么“模型会用工具”不等于“模型能可靠完成任务”。工具把手伸到了外部世界，但没有自动提供判断：这次调用是否有必要、结果是否可信、下一步是否该换路线。

### 2. 服务端还在做一轮翻译和守门

#### ① 历史不是一直原样塞回去

我的 adapter 会根据 `previous_response_id` 或 conversation 链展开此前的 input 项，再把 Responses 结构转成上游模型需要的 chat body。**状态展开**解决的是“这次请求怎样接上上次”，不是“模型已经理解了之前发生的一切”。

长对话里尤其容易混淆这两件事。保留历史能让模型看见旧信息，却不会自动把旧信息压缩成结论，更不会自动区分“已经证实的事实”和“上次随手猜的原因”。

#### ② 工具调用前后，都需要确定性的检查

服务端还会过滤不兼容工具，注入受控的环境信息，并在调用前做工具预检。例如，补丁结构不合法或命令方言不匹配，都可以返回给模型纠正。**预检**像代码 review 的门禁，它能拦住一部分确定性错误。

但预检也只是门禁。它能说“这次补丁格式错了”，却不能单独回答“这个补丁是否真的修好了用户的问题”，更不能替团队决定把它装进长期运行的 Agent。

## 二、今天常见的 Agent，已经解决了哪些问题

### 1. ReAct、记忆和重试，让 Agent 能继续往前走

#### ① 它们擅长把一次任务跑得更长

观察、行动、再观察的循环，让 Agent 能根据工具返回值调整下一步。**ReAct 式循环**解决的是单次任务里的“看见外部结果以后继续做什么”，这已经比只生成一段文本强很多。

记忆系统则把用户偏好、项目约定和过去摘要留到下一次会话。规划器会先拆任务，再按计划调用工具；重试器会在失败后换参数、换命令或再试一次。这些机制都很实用，我自己也一直在用。

#### ② 它们通常不负责长期改造自己

问题出在任务结束以后。一次 retry 成功，可能只是运气好；一段反思写得很像样，也可能没有改变下一次行动。**轨迹**记录了发生过什么，却不天然等于“以后应该怎样修改系统”。

很多 Agent 会把经验塞进 memory，或改一段 prompt。这适合轻量调优。可一旦要改工具、技能、模型路由、配置甚至执行 runtime，问题就变成了工程变更：改动范围、测试、兼容性、部署和回滚，缺一项都会让“自进化”变成难以复盘的试错。

### 2. refine 把问题推进了一步，但仍要面对运行时治理

#### ① refine 是一种很有价值的协议

一些 Agent 系统会提供 refine：任务结束后读取轨迹，对提示词、记忆、技能或 harness 状态做一次小步修改。**refine**把“下次试试”变成了有状态的更新。这比无限重试更接近学习。

它的难点不在于再调用一个模型，而在于修改如何被约束。谁冻结修改前的状态，谁检查并发冲突，谁保存 before/after，失败后怎么回到旧版本，这些决定了 refine 是经验积累，还是新的不稳定来源。

#### ② 常见系统往往把几种判断混在一起

一个模型既发现问题、提出改动、评价改动、决定上线，速度很快，风险也集中在同一处。**自评**在探索阶段可以提供方向，却不适合充当最终裁决。

我不认为所有任务都需要重型验证。改一段私有草稿和替换长期运行的工具，风险完全不同。问题是，当系统开始宣称“会自己变强”时，它至少要说明：它究竟改了什么，谁验证过，失败时能不能还原。

## 三、我理解的世界模型式自进化，先得有一套能落地的账本

### 1. 先分清事实、假设和候选

#### ① 失败不是结论，它只是观察

工具报错、测试失败、用户纠正、任务停滞，这些都只是**事实**。它们说明外部世界给了负反馈，却不直接说明应该怎么修。

接下来系统需要形成假设，例如“并行工具的 prepare 阶段被串行等待了”。假设必须能被反驳：要么写一个最小测试，要么做一次受控对照。把“我觉得”改成“我能怎样证明自己错了”，才有继续讨论的价值。

#### ② 候选是一场受限实验

假设成立之前，系统只能提出**候选改动**。候选要有固定的修改范围、修改前后内容、预期结果和可复现入口。这样验证失败时，失败能被定位到某次实验，而不是混进一堆后续操作里。

这套分法听起来朴素，却能把很多混乱的 Agent 轨迹拆开：模型的解释不是事实，工具的输出不是结论，一次成功也不是长期能力。

### 2. 世界模型不是一个名词，它是一条反馈链

#### ① 有状态，不等于已经有世界模型

给 Agent 加 memory、摘要和向量检索，能让它记住更多东西。**状态**只有在能支持预测、检验和修正时，才逐渐接近世界模型的角色。

我更愿意把“世界模型式 Agent”理解成一条工程路线：它不只保存文本，还要保存事实来源、当前假设、实验结果、被拒绝的候选和仍然未知的边界。下次遇到相似问题时，它能知道哪些路已经走不通。

#### ② 真实世界要保留否决权

模型可以提出修复方案，但测试、隔离执行、真实任务回放和外部验证器要能拒绝它。**反馈链**必须允许外部结果推翻模型。

这也是我认为“可信自进化”比“自动改 prompt”难得多的地方：系统要同时保留创造性和否决权，还要让每次否决成为下一轮可用的证据。

## 四、什么样的自进化，才配得上“通用”两个字

### 1. 一切可替换，才不会把学习锁死在 prompt 里

#### ① Agent 的能力不只是一段 system prompt

工具、技能、配置、模型路由和执行 runtime 都会改变 Agent 的行为。**可替换对象**越丰富，系统就越有机会把不同类型的失败转成不同类型的修复。

例如，读不到文件可能需要补工具；总是输出错格式可能需要技能；超时可能是配置问题；复杂任务的执行策略也可能需要独立 runtime。把所有问题都交给 prompt，往往只是在一个过载的入口上打补丁。

#### ② 可替换不等于验证链也能被替换

通用性还有另一面：有些部分必须锁住。**信任根基**里的 verifier、gate、回归集和权限边界，不能由正在被评估的候选随手修改。

否则系统会落入一个循环：候选先改掉检查自己的规则，再宣布自己通过。开放需要明确边界；边界内的对象可以被提出、验证、安装，也可以被拒绝。

### 2. 这里才轮到 Loom 出场

#### ① Loom 想补的是控制面

Loom 的方向，是把观察到的失败、显式假设、候选、独立验证、cold apply 和 rollback 放到一个外部控制面里。**控制面**负责让重要改动有证据、有边界、有撤回路径。

这篇文章先停在问题和方法。后续案例会拆开两条证据链：一条是 Agent 生成 refine skill 后，经真实 Loader 加载并回滚；另一条是 scheduler 的 prepare 串行问题如何被修复，并在受控 workload 下留下可复查的数据。

#### ② 现在还不能把 Loom 说成什么

Loom 目前还没有证明通用世界模型，也没有证明任意 Agent 都能稳定改好复杂代码。**边界**必须先说在前面：局部 scheduler 改善不能外推为整体性能；单个真实任务的成功也不能外推为多任务成功率。能生成 skill，同样不能证明任意模型都会遵循它。

我愿意把这些限制写出来。值得积累的是一套以后还能继续被反驳、补充和复用的实验记录。

## 写在最后

我觉得今天的 Agent 已经很会行动，却还不擅长从行动里可靠地成长。**自进化**需要一套长期工程：把失败变成事实，把判断写成假设，把改动关进可验证的范围，再把通过和拒绝都留下来。

如果这条路能继续走下去，Agent 的经验就不再只是上下文里的一段总结。它会成为一组可以检查、复跑、撤回，也可以交给下一轮 Agent 继续使用的系统状态。
